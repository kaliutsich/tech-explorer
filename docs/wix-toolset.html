WiX Toolset from simple to advanced

This guide is written as a practical build recipe: we start with a tiny MSI, then grow it into a production-grade installer that deploys a Windows Service hosting a Kestrel-based .NET Web API, plus a Windows-installed PWA that talks to that local API. We also cover upgrades, logging, prerequisites via Burn, and deployment via Intune/SCCM style workflows.

WiX v4 MSI Burn Upgrades Logging CI/CD

1. What we are building (POC target)

1.1 Components

  • PWA: browser-based UI, installable on Windows (from Edge/Chrome). It runs as a desktop-like app, but it is still web tech.
  • .NET Web API: Kestrel-hosted local API, exposed on http://127.0.0.1:PORT (or a named pipe in advanced variants).
  • Windows Service: controls lifecycle (start on boot, restart on failure, runs under a chosen identity), and hosts the .NET Web API.
  • Installer (MSI): lays down files, registers the service, sets config, opens firewall if needed, creates logs folders, and sets ACLs.
  • Optional bootstrapper (Burn): installs prerequisites (e.g., .NET Hosting Bundle / Desktop Runtime), then installs the MSI.

1.2 Typical flow at runtime

PWA (installed from browser) └─ calls local API (localhost) for filesystem / device / local workflows └─ .NET Web API hosted by Windows Service └─ uses OS resources (filesystem, certificates, local databases, etc.)
Key architectural point: the MSI does not “install the PWA” in the same way it installs EXEs. A PWA is usually installed by the browser based on a manifest + service worker. Your MSI can still install the static web assets locally and register a start shortcut that opens the PWA URL, but the actual “install” experience is browser-driven unless you build a custom wrapper.

1.3 Why WiX fits

  • Enterprise-friendly deployment: MSI is still the standard for Intune/SCCM/GPO software distribution.
  • Deterministic installs and upgrades: stable component rules, repair, rollback, logging.
  • Precise OS integration: services, ACLs, registry, firewall, shortcuts.

2. The minimum you must understand about MSI (before writing WiX)

2.1 Product, Package, Feature, Component (the core model)

  • Product: the logical application. Identified by ProductCode. Changes on major upgrade.
  • Package: the MSI database file. Identified by PackageCode. Changes every build.
  • Feature: user-selectable grouping. Most apps have one “Complete” feature.
  • Component: the atomic install unit. A component is what MSI tracks for install/repair/uninstall.
The single most common MSI mistake: mixing files across components incorrectly or changing component GUIDs randomly. This breaks upgrades, causes “ghost files”, and makes repair unpredictable.

2.2 KeyPath and how MSI knows “is this installed?”

  • A component must have a KeyPath resource (often a file, sometimes a registry value).
  • MSI uses KeyPath to detect if the component is present and consistent.
  • If KeyPath disappears, MSI may trigger self-repair (depending on advertisement and usage).

2.3 Upgrades 10-second summary

  • Major upgrade: new ProductCode, same UpgradeCode, version increases. Old version removed.
  • Minor upgrade: same ProductCode, version changes within allowed rules. Rarely used these days.
  • Patch (MSP): diff-based patching. Advanced, use only if you really need it.
For most modern apps: do major upgrades only, keep it boring, predictable, supportable.

3. Tooling setup (WiX v4, CLI-first)

3.1 Install WiX v4

WiX v4 is the modern line. If you are stuck with v3, keep the structure, but commands/extensions differ.

# One common approach (example): # - install wix toolset v4 via official installer or package manager # - ensure 'wix' is available in PATH wix --version

3.2 Recommended repo layout

/src /ServiceHost # .NET Windows Service hosting Kestrel /PwaApp # PWA static assets (or source) /Installer /wix Product.wxs Fragments/ Includes/ Assets/ build.ps1 build.cmd

3.3 Build outputs to feed WiX

  • .NET publish output: self-contained or framework-dependent (you decide).
  • PWA output: static files (dist) if you build with Vite/React/etc.
# Example: publish service host dotnet publish .\src\ServiceHost\ServiceHost.csproj -c Release -o .\artifacts\service # Example: build PWA # (depends on your toolchain) pnpm install pnpm build # output: .\src\PwaApp\dist -> copy to .\artifacts\pwa

4. Start simple: your first MSI installs one file

4.1 Minimal WiX project (concept)

Step one is not “install the whole system”. Step one is “create an MSI that installs one file to Program Files”. Once this works reliably, you add complexity one layer at a time.

4.2 Minimal Product.wxs skeleton (WiX v4 style)

<?xml version="1.0" encoding="utf-8"?> <Wix xmlns="http://wixtoolset.org/schemas/v4/wxs"> <Package Name="MyPOC" Manufacturer="MyCompany" Version="1.0.0" UpgradeCode="{PUT-YOUR-UPGRADECODE-GUID-HERE}"> <MajorUpgrade DowngradeErrorMessage="A newer version is already installed."/> <MediaTemplate /> <Feature Id="MainFeature" Title="MyPOC" Level="1"> <ComponentGroupRef Id="MainComponents" /> </Feature> </Package> <Fragment> <StandardDirectory Id="ProgramFilesFolder"> <Directory Id="INSTALLFOLDER" Name="MyPOC"> <ComponentGroup Id="MainComponents" Directory="INSTALLFOLDER"> <Component> <File Source="..\..\artifacts\service\readme.txt" /> </Component> </ComponentGroup> </Directory> </StandardDirectory> </Fragment> </Wix>

4.3 Build it

# Example WiX v4 build invocation pattern # (exact commands depend on your setup; keep it in your build script) wix build .\src\Installer\wix\Product.wxs -o .\artifacts\installer\MyPOC.msi
Success criteria for this section: you can install, repair, uninstall; and the file lands exactly where you expect.

5. Add the .NET service host payload (still no service registration)

5.1 Decide: framework-dependent vs self-contained

  • Framework-dependent: smaller MSI, requires .NET runtime installed (handled by Burn or enterprise baseline).
  • Self-contained: larger MSI, fewer external prerequisites, but you ship more bits and update more often.

5.2 Install the entire publish directory

You normally do not list 200 files by hand. Use harvesting (carefully) or generate fragments at build time.

5.3 Harvesting (safe-ish pattern)

Harvesting means generating WiX fragments from a folder. The danger is unstable component GUIDs. The mitigation is stable component IDs and controlled harvesting.

Treat harvesting as codegen: commit generated fragments or generate them deterministically in CI. Do not “harvest random” every time and hope upgrades work.
# Example idea (conceptual): # - harvest artifacts\service into a fragment file # - then wix build includes that fragment # # Your build script may: # 1) dotnet publish # 2) wix harvest ... -> ServiceFiles.wxs # 3) wix build Product.wxs ServiceFiles.wxs

5.4 Keep a dedicated folder

INSTALLFOLDER \Service ServiceHost.exe ServiceHost.dll appsettings.json ...

6. Add Windows Service registration (core of the POC)

6.1 What we want from the service

  • Auto-start on boot.
  • Restart on failure (configured via service recovery options).
  • Runs under a chosen identity (LocalService, NetworkService, or a dedicated user).
  • Writes logs to a known location (ProgramData recommended).

6.2 Service identity selection (practical)

  • LocalService: low-privilege local account. Good default for local-only services.
  • NetworkService: can authenticate to network as the machine account. Use if you need domain/network resources.
  • Dedicated user: best control, but requires password management and ACL setup.
For a localhost-only API that mostly touches local filesystem: LocalService is often enough, plus explicit ACLs on folders it must access.

6.3 ServiceInstall and ServiceControl (WiX extensions)

In WiX, service installation usually uses the Util extension (varies between WiX versions). Conceptually:

<Component Id="cmp_Service" Guid="{PUT-STABLE-GUID-HERE}"> <File Source="..\..\artifacts\service\ServiceHost.exe" KeyPath="yes" /> <!-- Service installation metadata --> <ServiceInstall Id="svcInstall" Name="MyPOC.ServiceHost" DisplayName="MyPOC Local API" Description="Hosts the local .NET Web API for the PWA" Start="auto" Type="ownProcess" ErrorControl="normal" /> <ServiceControl Id="svcControl" Name="MyPOC.ServiceHost" Start="install" Stop="both" Remove="uninstall" Wait="yes" /> </Component>
The exact XML element names and namespaces depend on WiX v4 extensions you include. This guide shows the “what”; your implementation must match the actual extension schema you reference.

6.4 Service recovery (restart on failure)

Windows service recovery is not always covered by plain ServiceInstall. Common pattern:

  • Set recovery via a custom action calling sc.exe failure or PowerShell.
  • Or use a supported WiX extension element if available in your version.
# Example PowerShell (conceptual): sc.exe failure "MyPOC.ServiceHost" reset= 86400 actions= restart/5000/restart/5000/restart/5000 sc.exe failureflag "MyPOC.ServiceHost" 1
If you do this via custom action, do it as deferred + elevated, and make sure rollback is sane. Custom actions are where many MSI setups become fragile.

7. Configure Kestrel for a local-only API

7.1 Port selection strategy

  • Fixed port (simple): e.g., 5123. Easier firewall rules and support docs.
  • Dynamic port (advanced): write selected port to config/registry and let PWA discover it.
  • Named pipe (advanced): avoids port conflicts and firewall questions, but needs client support.

7.2 Avoid exposing beyond localhost

  • Bind to 127.0.0.1 only.
  • Do not bind to 0.0.0.0 unless you explicitly want LAN access.
  • Consider simple auth even on localhost if you have sensitive operations.
# Example appsettings.json idea: { "Kestrel": { "Endpoints": { "Http": { "Url": "http://127.0.0.1:5123" } } }, "Logging": { "LogLevel": { "Default": "Information" } } }

7.3 Where installer-owned config should live

  • Immutable binaries: Program Files.
  • Mutable config & logs: ProgramData (common), or a dedicated folder with ACLs.
When you place config in Program Files, you often require admin rights to edit it later. That is sometimes okay, but operationally ProgramData is usually easier.

8. PWA packaging strategy (realistic options)

8.1 Option A: classic PWA served from a public URL

  • Pros: simplest, browser handles install and updates naturally.
  • Cons: requires internet and a stable URL, may be tricky in offline environments.

8.2 Option B: local static site served by the same Windows Service

  • Service hosts two things:
    • Static files for UI
    • API endpoints
  • User opens http://127.0.0.1:5123, sees UI, and installs PWA from there.
  • Works offline. MSI updates both UI and API.
For your POC (PWA + local API), Option B is usually the most coherent: one service hosts everything locally.

8.3 Option C: MSI installs “web assets”, browser installs PWA later

  • MSI lays down PWA files into Program Files.
  • MSI creates a shortcut that opens Edge/Chrome to the local URL.
  • User clicks “Install app” in the browser UI.

8.4 What WiX can actually do here

  • Install the static UI files to a folder used by the service.
  • Create shortcuts (Start menu, Desktop) that open the local UI URL.
  • Register URL protocol handlers if you want a custom mypoc:// scheme (advanced).

9. File locations, logs, and ACLs (supportable installs)

9.1 Recommended layout on disk

Program Files \MyPOC \Service (binaries) \Assets (static PWA assets if hosted locally) ProgramData \MyPOC \config \logs \data

9.2 ACL rules (common scenario)

  • Service runs as LocalService.
  • Service needs write access to ProgramData\MyPOC\logs and ProgramData\MyPOC\data.
  • Installer sets ACLs during install.
The exact WiX elements depend on extension support. If the extension is not available, you can set ACLs via a carefully written deferred custom action.

9.3 Do not write logs into Program Files

  • Program Files is for immutable, admin-owned binaries.
  • Writing there causes permission issues and messy support stories.

10. Shortcuts and user experience

10.1 Start menu shortcut to local UI

You can create a shortcut that launches the browser to the local UI: http://127.0.0.1:5123.

10.2 First-run experience pattern

  • Installer installs and starts the service.
  • Installer optionally opens the UI at the end (optional checkbox).
  • User optionally installs the PWA from browser UI (if you are using the standard PWA install flow).
Auto-opening browsers and auto-installing PWAs can conflict with enterprise policies. Keep it conservative by default.

11. Burn bootstrapper for prerequisites (advanced but common)

11.1 When you need Burn

  • Framework-dependent service host requires .NET runtime (or hosting bundle).
  • You want one “setup.exe” that installs prerequisites then the MSI.
  • You need prerequisite detection and conditional chains.

11.2 Typical chain

Setup.exe (Burn bundle) 1) Detect .NET runtime 2) If missing, install runtime (silent) 3) Install MyPOC.msi 4) Log everything to a known location
In enterprise deployments (Intune/SCCM), sometimes you skip Burn and rely on baselined runtimes. But for a standalone installer, Burn is often the cleanest UX.

12. Upgrades that do not break (the rules you actually follow)

12.1 Use MajorUpgrade

  • Keep one UpgradeCode forever for the product line.
  • Bump Product Version each release.
  • Let MajorUpgrade remove previous versions automatically.

12.2 Stable component GUIDs

  • Every component must have a stable GUID.
  • If the key path resource identity changes “meaningfully”, you may need a new component.
  • If you keep changing GUIDs randomly, MSI cannot reason about upgrade and repair.

12.3 Services during upgrade

  • Stop service before replacing binaries.
  • Replace binaries.
  • Start service afterwards.
If your service holds file locks, the upgrade sequence matters. Make sure ServiceControl stop happens early enough and you wait for stop.

12.4 Data preservation

  • Data under ProgramData should remain across upgrades by default.
  • On uninstall, decide whether to remove data (usually keep it unless user explicitly chooses “remove data”).

13. Logging and supportability (MSI logs + service logs)

13.1 MSI logging

For troubleshooting, you almost always want a verbose MSI log:

msiexec /i MyPOC.msi /l*v install.log

13.2 Where service logs should go

  • ProgramData\MyPOC\logs is a good default.
  • Optionally also write to Windows Event Log for high-level lifecycle events.

13.3 Service troubleshooting quick commands

sc query "MyPOC.ServiceHost" sc start "MyPOC.ServiceHost" sc stop "MyPOC.ServiceHost" # Event Viewer: Windows Logs -> Application/System # (if you log there)

14. CI/CD integration (Azure DevOps oriented)

14.1 Build pipeline steps (high-level)

  1. Restore/build PWA
  2. Build/publish .NET service host
  3. Generate/harvest WiX fragments (if you use harvesting)
  4. Build MSI
  5. Optionally build Burn bundle (setup.exe)
  6. Sign artifacts (if required)
  7. Publish artifacts

14.2 Version stamping

  • Single source of truth for version: pipeline variable (e.g., 1.4.12).
  • Use it for:
    • .NET assemblies
    • MSI Version
    • Bundle version
In MSI, Version has rules (max 3 numeric fields). If you need semver build metadata, keep it in a separate property or file, not in MSI Version.

15. Enterprise deployment (Intune/SCCM style)

15.1 What enterprises like

  • Silent install: no UI, deterministic exit codes.
  • Reliable detection: registry keys / product code detection.
  • Repairable and uninstallable with logs.

15.2 Common silent commands

# Silent install msiexec /i MyPOC.msi /qn /norestart # Silent uninstall (product code or cached msi) msiexec /x {PRODUCT-CODE-GUID} /qn /norestart

15.3 Detection rules (idea)

  • Registry key under HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall
  • Or a custom registry marker you create as part of install
  • Or service presence + version file in install folder
Service presence alone can be a weak detector if someone manually deletes it. Prefer MSI product detection where possible.

16. Advanced topics (when you want to level up)

16.1 Avoid ports entirely: named pipes

If you want to eliminate port conflicts and firewall discussions, use named pipes. Your PWA then needs a bridge (because browsers cannot directly talk to named pipes). Typical solution: still expose localhost HTTP, but keep it locked down and authenticated.

16.2 Certificate and trust model

  • If you use HTTPS on localhost, you must manage certificates.
  • Installing certs into local machine stores is sensitive and must be carefully justified.

16.3 Offline-first PWA updates

  • Service worker caching strategy matters.
  • MSI upgrades update static assets, but service worker may keep old cached content.
  • Provide a cache-busting strategy (versioned assets, SW update flows).
PWA caching bugs are a top source of “but I updated and UI is still old” incidents. Plan your cache invalidation deliberately.

17. Troubleshooting checklist (fast triage)

17.1 Install fails

  • Run with verbose MSI log: /l*v.
  • Check if service user/identity has permissions.
  • Check file locks (service running while upgrading).
  • Check custom action failures (they are frequent failure points).

17.2 Service does not start

  • Check service account rights.
  • Check config file paths.
  • Check logs in ProgramData.
  • Try running the exe manually from console for immediate error output (if applicable).

17.3 PWA can’t talk to localhost API

  • Verify the service is running and listening on 127.0.0.1.
  • Check mixed-content rules if PWA is HTTPS but API is HTTP (browser security rules apply).
  • Consider CORS and origin policies (localhost origins are still origins).
